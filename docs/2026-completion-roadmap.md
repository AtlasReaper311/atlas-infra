# 1. Executive outcome
Atlas Systems is no longer mainly constrained by missing capabilities. The estate already contains infrastructure, observability, incident evidence, dependency automation, public interfaces, local AI, model evaluation, recovery tooling, architecture analysis, interactive Labs and sonification systems.

| PROGRAMME ORDER CLOSE -> PROVE -> INTEGRATE -> EXPLAIN -> EXPAND -> FREEZE |
| --- |

The objective is not to maximise repository count. The objective is to make the existing estate coherent, evidence-led, current, portfolio-ready and safe to leave at lower intensity when the honours project begins in January 2027.
## Five questions Atlas should answer by 31 December
1.  What exists? Estate inventory and classifications come from current authoritative sources.
2.  What is actually running? Source, review, merge, deployment, runtime verification and live verification are separate states.
3.  How do the systems relate? The site explains one connected engineering estate rather than unrelated repositories.
4.  What happens when something changes or fails? Change, impact, incident and recovery evidence can be followed.
5.  What is finished, deferred or blocked? The final audit leaves explicit stop states rather than background ambiguity.

# 4. Programme operating rules
## Maximum work in progress
Keep no more than two major Atlas source workstreams active at once, excluding routine dependency review.
## Merge is not rollout
Use source -> validation -> draft PR -> exact-head review/checks -> merge gate -> authorised merge -> separate rollout gate -> authorised rollout -> live verification.
## Current truth wins
Inspect current repository instructions, ADRs, policies, validators and provider/live evidence before production advice or implementation.
## No new repo without a boundary
Require an independent deployment, security, release, reusable-package or data/runtime ownership boundary.
## Do not encode volatile facts manually
Generate repository counts, active state and evidence summaries from authority.
## Uncertainty is valid
UNKNOWN, NOT OBSERVED and NOT APPLICABLE must remain first-class states.
## Security boundaries remain fixed
Public evidence uses safe projections only. Read-only evidence systems do not gain mutation permissions.

# Phase 1 - Formalise evidence lifecycle and generated estate truth

| PHASE | WINDOW | PRIORITY | THEME |

| 1 | 7 Sep - 27 Sep | Mandatory | Define what Atlas Systems is allowed to claim |

## Objective
Create one formal evidence model that the control plane and future Evidence Console can share. At the same time, stop manually maintaining volatile estate snapshots.
## 1.1 Part 0 architecture inspection
- Current atlas-infra ADRs.
- Rollout-board policy and implementation.
- Estate registry and public-assurance inputs.
- Deterministic public classification projection.
- atlas-api-public presentation contracts.
- atlas-systems current data consumption.
- atlas-twin evidence/change-impact contracts.
- Current deployment/public evidence capabilities.
## 1.2 Evidence lifecycle
Prefer an accepted atlas-infra ADR if the model is estate-wide.
### Evidence record fields
- Subject: repository, PR, commit, deployment, service, interface, model promotion, article, incident, restore drill.
- Assertion: what fact is being claimed.
- Source/provenance: where the evidence came from.
- Exact identifier: commit, run, deployment version, artifact or other immutable reference.
- Observed time: when the evidence was collected.
- Result: PASS, FAIL, UNKNOWN, NOT OBSERVED or NOT APPLICABLE.
- Scope: what the evidence proves and what it does not prove.
## 1.3 Lifecycle profiles
### Runtime Worker
SOURCE -> CHECKED -> MERGED -> DEPLOYED -> RUNTIME VERIFIED -> LIVE VERIFIED
### Static/public site
SOURCE -> CHECKED -> MERGED -> DEPLOYMENT OBSERVED -> BROWSER VERIFIED
### Library/toolkit
SOURCE -> CHECKED -> MERGED -> RELEASED where applicable
### Documentation/policy
SOURCE -> CHECKED -> MERGED -> PUBLISHED/PROJECTED where applicable
### Model promotion
EVAL PREPARED -> EVAL PASSED -> HUMAN REVIEWED -> PROMOTION APPROVED
### Article
AUTHORED -> VALIDATED -> SCHEDULED -> SCHEDULER EXECUTED -> LIVE VERIFIED
## 1.4 Generate the estate snapshot
- Discover owned repositories from GitHub.
- Read atlas-infra classification authority inputs.
- Use deterministic classification projection.
- Use presentation manifest for topology only, not classification authority.
- Emit machine-readable JSON and human-readable Markdown.
- Carry generation timestamp and source versions where practical.
- Warn on missing or contradictory authority.
## 1.5 Drift detection
- Public repository missing required classification.
- Projection differs from authority inputs.
- Presentation data conflicts with classification authority.
- Hand-maintained snapshot count differs from generated truth.
- Duplicate or ambiguous ownership.
## Phase 1 deliverables
- Accepted evidence lifecycle architecture.
- Lifecycle profiles.
- Generated estate snapshot tool.
- Machine-readable and human-readable outputs.
- Drift validator/tests.
- Plan for replacing stale manual snapshots.

| EXIT GATE A reviewer can take any repository and identify its lifecycle, required evidence, authority source and the exact state Atlas must show when evidence is missing. |

| PHASE | WINDOW | PRIORITY | THEME |

## Objective
Build a read-only flagship that explains why Atlas believes a technical state is true. Default ownership should remain in atlas-systems unless Part 0 proves a separate runtime/security boundary.
## 2.1 One complete vertical slice
Start with one real change and carry it through SOURCE -> CHECKS -> REVIEW -> MERGE -> DEPLOYMENT -> RUNTIME -> LIVE.

| REQUIRED UNCERTAINTY BEHAVIOUR If deployment is not observed, display MERGED - DEPLOYMENT NOT OBSERVED - NOT LIVE VERIFIED. Never infer the missing steps. |
| --- |

## 2.2 Core views
### Change view
What happened to this change? Show PR, exact commit/head, checks, merge, deployment, runtime, browser/live evidence, timestamps and gaps.
### Service view
What evidence exists for this running service? Show owner, expected contract, latest observed deployment/version, runtime evidence and staleness.
### Estate view
Where is evidence complete, stale, unknown or not applicable across the estate? Avoid a generic green-dot dashboard.
### Evidence detail
Where did a claim come from, when was it observed, and what does it actually prove?
## 2.3 Add four lifecycle archetypes
1.  Static/public interface.
2.  Worker/runtime service.
3.  Non-runtime repository/toolkit.
4.  Publication or model-promotion subject.
## 2.4 Integrate Atlas Twin carefully
Use Twin for impact/relationship context, not deployment authority. Change evidence says what changed. Twin says what could be affected. Live evidence says what was actually observed.
## 2.5 UX and evidence requirements
- UNKNOWN visually distinct from FAIL.
- No generic green badge without evidence text.
- Chronological evidence chain.
- Observation time and stale-state visibility.
- Keyboard, mobile and reduced-motion support.
- Current Atlas interface contracts.
- Synthetic/demo evidence labelled separately from observed evidence.
- Public-safe projection only.
## Phase 2 deliverables
